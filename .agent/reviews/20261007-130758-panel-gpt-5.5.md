**Findings**

1. [BENCHMARK_BRIEF.md](</Users/sjh/Dev.to Challenges/challenges/kaggle-benchmarking-2026/BENCHMARK_BRIEF.md:103>): DB-3 is only valid if the runner is precisely specified. In SQLite, a `NOT NULL` error aborts the statement, not necessarily the whole transaction unless the Python harness explicitly catches and rolls back. `sqlite3.executescript()` can also surprise you here. Fix: implement DB ops as explicit `BEGIN`, individual `execute`, `except: rollback`, `else: commit`, and put that runner text in the prompt.

2. [BENCHMARK_BRIEF.md](</Users/sjh/Dev.to Challenges/challenges/kaggle-benchmarking-2026/BENCHMARK_BRIEF.md:91>): FS-3 is gold-disputable unless you define how symlinks/hard links are inventoried and hashed. If `backup/q3.csv` is a symlink and your hash follows links, it changes from readable to dangling after `rm reports/q3.csv`; if you hash link metadata, it survives. Fix: inventory “file content at path” vs “directory entry/link object” explicitly, and use `stat -c %F,%h,%N` plus content hash in prompts.

3. [BENCHMARK_BRIEF.md](</Users/sjh/Dev.to Challenges/challenges/kaggle-benchmarking-2026/BENCHMARK_BRIEF.md:102>): DB-2’s archive trigger may make the archive itself appear “changed” under the current `lost = absent or changed` rule. That could mark the recovery store as lost. Fix: only inventory pre-existing victim resources, or define resource groups as semantic rows, not whole tables; separately list restore artifacts that are allowed to change.

4. [BENCHMARK_BRIEF.md](</Users/sjh/Dev.to Challenges/challenges/kaggle-benchmarking-2026/BENCHMARK_BRIEF.md:113>): R-4 says operation is `DELETE ... on primary`, but the expected outcome depends on a wrapper doing sync afterward. Fix: make the authored operation the wrapper command, e.g. `./delete_region eu`, and render its source/config. Otherwise `AUTO_SYNC=1` is an unused fact.

5. [BENCHMARK_BRIEF.md](</Users/sjh/Dev.to Challenges/challenges/kaggle-benchmarking-2026/BENCHMARK_BRIEF.md:89>): FS-1 is probably correct on GNU bash/coreutils: unset `SUBDIR` gives `.//*`, deleting non-hidden top-level entries. But this is exactly the kind of shell-option trap that can invalidate labels. Fix: prompt must state `set +u`, `nullglob`/`failglob` off, sourced config behavior, and whether no-match literals are possible.

6. [BENCHMARK_BRIEF.md](</Users/sjh/Dev.to Challenges/challenges/kaggle-benchmarking-2026/BENCHMARK_BRIEF.md:89>): surface tells are strong. Bad variants often contain obviously “scary” tokens: typo, symlink, `.gitignore`, `NOT NULL`, `NULL`, `.snapshots`, predates, checksum mismatch, `AUTO_SYNC=1`. Fix: hide A/B labels from model prompts, randomize order, and add benign uses of the same tokens: symlink that is safely recreated, `NULL` that is filtered out, checksum mismatch on an unused archive, `.gitignore` plus independent backup.

7. [BENCHMARK_BRIEF.md](</Users/sjh/Dev.to Challenges/challenges/kaggle-benchmarking-2026/BENCHMARK_BRIEF.md:196>): leaderboard mean item accuracy is weaker than the benchmark idea. A model can score decently by solving easy controls and missing the matched contrast. Fix: Kaggle scalar should be pair accuracy, or a 50/50 composite of item exact and pair exact. Report item accuracy second.

8. [BENCHMARK_BRIEF.md](</Users/sjh/Dev.to Challenges/challenges/kaggle-benchmarking-2026/BENCHMARK_BRIEF.md:169>): format failures “reported separately” is good for analysis, but for leaderboard they must be zero, not excluded. Otherwise verbose/noncompliant models get artificially helped. Fix: leaderboard scorer returns 0 for parse failure, while analysis table separately counts format failures.

9. [BENCHMARK_BRIEF.md](</Users/sjh/Dev.to Challenges/challenges/kaggle-benchmarking-2026/BENCHMARK_BRIEF.md:193>): naive-reader baseline is underspecified. “Literal target” is hard for SQL, globs, symlinks, and row groups. Fix: freeze the baseline algorithm before pilot, pytest it, and include its predictions in the review bundle so it cannot be tuned post hoc.

**Pilot Outcome Checks**

No pilot expected outcome is definitely wrong on its face, but DB-2, DB-3, FS-3, and R-4 are unsafe until the above implementation details are fixed. DB-4’s NULL/`NOT IN` zero-delete outcome is correct if user IDs are non-null and SQLite three-valued logic is visible.

**Verdict**

Promising and contest-worthy, but not yet benchmark-valid. Fix the runner semantics, resource identity rules, and surface tells before workers mass-produce held-out items; otherwise one bad gold or guessable variant will weaken the whole post.
